1. Introducción

En este documento se recogen todas las pruebas realizadas sobre la API REST de ChangeOrg, desarrollada con Laravel 12. El objetivo es comprobar que todos los endpoints devuelven las respuestas correctas tanto en situaciones normales como cuando se producen errores. Para ello utilizo Postman, configurando una colección con variables de entorno para no tener que repetir la URL base ni el token en cada petición.

La API sigue un formato de respuesta estándar: cuando todo va bien devuelve success: true junto con los datos y un mensaje, y cuando hay algún error devuelve success: false con el mensaje de error y, si procede, los detalles de validación.

Los recursos que cubre la API son: Usuarios (registro y autenticación con JWT), Categorías, y Peticiones (con soporte para archivos adjuntos y firma de peticiones por otros usuarios).

2. Configuración del entorno en Postman

Antes de empezar las pruebas creo una colección en Postman llamada ChangeOrg API – Laravel 12 y defino las siguientes variables de colección:

VariableValor inicialPara qué sirve
base_urlhttp://localhost:8000/apiURL base de la API
token(vacío)Token JWT del usuario 1, se rellena automáticamente tras el login
token2(vacío)Token JWT del usuario 2, necesario para las pruebas de autorización
petition_id1ID de la petición creada, se actualiza al crear una nueva

En la cabecera Authorization de las rutas protegidas uso el tipo Bearer Token con el valor {{token}}. Así cuando el login guarda el token automáticamente, todas las demás peticiones ya lo usan sin tocar nada.

El servidor de Laravel tiene que estar corriendo con php artisan serve y la base de datos tiene que tener al menos alguna categoría cargada. Para eso ejecuto los seeders o inserto manualmente alguna categoría antes de empezar.

3. Autenticación

La API usa JWT (JSON Web Tokens) para la autenticación. Primero hay que registrar un usuario y luego hacer login para obtener el token. A partir de ahí ese token va en la cabecera Authorization: Bearer {token} en todas las peticiones protegidas. Para las pruebas de autorización registro dos usuarios distintos.

3.1 Registro de usuario

Endpoint: POST /api/register | Acceso: Público

Este endpoint permite crear una cuenta nueva. Requiere nombre, email y contraseña (mínimo 6 caracteres). Si todo está bien devuelve el código 201 con los datos del usuario creado. Si hay algún problema de validación devuelve 422.

OK Registro correcto – 201

Envío los datos correctos de un nuevo usuario y compruebo que se crea sin problemas.

POST {{base_url}}/register
Body (JSON):
{
  "name": "Usuario Test",
  "email": "test@test.com",
  "password": "123456"
}

Respuesta esperada (201):

{
  "message": "Usuario registrado correctamente",
  "user": {
    "id": 1,
    "name": "Usuario Test",
    "email": "test@test.com"
  }
}
[ Captura: Registro correcto – Status 201 ]

ERROR Email ya registrado – 422

Intento registrar de nuevo el mismo email para ver que el sistema lo detecta como duplicado.

POST {{base_url}}/register
Body (JSON):

  "password": "123456"

6.2 Crear una petición

Endpoint: POST /api/petitions | Acceso: Requiere token

Para crear una petición el body tiene que ser form-data porque se envían archivos junto con los datos de texto. El campo files[] acepta imágenes en formato jpeg, png, jpg, gif o svg, con un tamaño máximo de 4 MB. Es obligatorio subir al menos un archivo.

OK Crear petición con imagen – 201

Headers: Authorization: Bearer {{token}}

  description  = Queremos que el ayuntamiento no construya en el parque.

  category     = 1

6.3 Actualizar una petición

Endpoint: PUT /api/petitions/{id} | Acceso: Requiere token + ser el propietario

Solo el usuario que creó la petición puede modificarla. Si otro usuario intenta actualizarla, la Policy devuelve un 403 Forbidden. Opcionalmente se puede adjuntar un nuevo archivo (campo file en singular, no array).

OK Actualizar como propietario – 200

Headers: Authorization: Bearer {{token}}
Body (form-data):

8. Conclusiones

Después de realizar las 41 pruebas se puede ver que la API responde correctamente en todos los escenarios. Los errores de validación están bien controlados con el código 422 y los mensajes de error son claros e indican exactamente qué campo ha fallado. La autenticación funciona correctamente: sin token se obtiene 401, y cuando el token es de un usuario que no tiene permisos se obtiene 403.

El sistema de policies es importante porque impide que un usuario pueda modificar o eliminar peticiones de otros usuarios, y también impide que alguien firme su propia petición o la firme más de una vez. El contador signeds se actualiza correctamente con cada firma.

Los archivos adjuntos se suben al storage público de Laravel y quedan asociados a la petición. Al eliminar una petición también se eliminan los archivos del disco para no dejar archivos huérfanos.
