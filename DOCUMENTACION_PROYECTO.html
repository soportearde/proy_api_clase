1. Visión general

Aplicación full-stack que replica las funcionalidades centrales de Change.org: cualquier persona puede crear una petición ciudadana, subir imágenes que la apoyan, consultarla, editarla y borrarla (si es su autor), o firmar peticiones ajenas.

Cuenta con dos zonas claramente separadas:

  • Zona pública / de usuario: navbar superior tipo Change.org, listado de peticiones, detalle, formularios de creación/edición, "Mis peticiones" y "Mis firmas".
  • Zona admin: panel independiente a pantalla completa con sidebar oscuro propio. Gestión total de peticiones y usuarios, con caché reactiva y actualización pesimista.

La seguridad es de doble capa: el frontend bloquea con guards (UX, evita pantallas inútiles) y el backend bloquea con middleware (es la barrera real, aunque alguien intente saltarse Angular).

2. Arquitectura y stack

Backend – Laravel 12

  • JWT con php-open-source-saver/jwt-auth (driver auth:api).
  • Eloquent ORM, migraciones y tabla pivote para firmas.
  • Storage público vía php artisan storage:link para servir imágenes.
  • Middleware personalizado IsAdmin para proteger rutas de administrador.
  • Policies para que solo el propietario edite/borre sus peticiones.

Frontend – Angular 20

  • Standalone components en toda la app (sin NgModules).
  • Signals como mecanismo principal de estado reactivo.
  • Functional Guards (authGuard, adminGuard).
  • HTTP interceptor funcional que añade el token automáticamente y refresca JWT al caducar.
  • Rutas hijas anidadas para el panel de administración.
  • Reactive forms en todos los formularios.
  • Bootstrap 5.3 importado desde styles.css con paleta corporativa sobrescrita.

5. Autenticación JWT

Flujo

  1. El usuario envía email+password a POST /api/login.
  2. Laravel valida con Auth::attempt, genera un JWT y lo devuelve junto con el objeto user.
  3. Angular guarda el token en localStorage (clave access_token) y los datos del usuario (clave user_data).
  4. El servicio AuthService actualiza dos signals: isLoggedIn y currentUser. La navbar reacciona automáticamente.
  5. El HTTP interceptor añade Authorization: Bearer <token> a todas las peticiones HTTP.
  6. Si una petición devuelve 401, el interceptor intenta POST /api/refresh y reintenta la original con el nuevo token.
  7. Si el refresh también falla, hace logout forzoso.

Componentes implicados

ArchivoResponsabilidad
app/auth/auth.tsServicio singleton: login, register, logout, refresh, getProfile, signals isLoggedIn/currentUser, helpers isAuthenticated() y isAdmin()
app/auth/auth-interceptor.tsInyecta el bearer, captura 401, refresca el token y reintenta; si refresh falla → logout
app/auth/auth.guard.tsCanActivateFn: bloquea rutas si no hay token
app/auth/admin.guard.tsCanActivateFn: bloquea /admin/** si role !== 'admin'
app/pages/loginForm de login. Tras login, si admin → /admin; si no → /petitions
app/pages/registerForm de registro. Tras OK navega a /login

Manejo de errores

  • Login: 401 → mensaje "email o contraseña incorrectos"; otros → "error inesperado".
  • Register: 409/422 → "este email ya está registrado"; otros → error genérico.
  • AuthController envuelve login/register/me/logout/refresh con try/catch + ValidationException para devolver 422 claros.

6. CRUD de peticiones

Listado público

GET /api/petitions devuelve un objeto paginado (3 por página) con título, descripción, autor, categoría y la primera imagen. El componente ListComponent guarda los resultados en una signal y los pasa por un computed() que aplica el filtro del buscador del navbar.

Detalle

GET /api/petitions/:id con with(['user','category','files']). El show-component muestra autor, fecha, estado, firmas y todas las imágenes. Si el usuario es el autor (compara currentUser().id === petition.user_id) aparecen los botones Editar y Borrar. Si está logueado y no es el autor aparece el botón Firmar petición.

Creación

Formulario reactivo con FormBuilder. Acepta multi-file (multiple accept="image/*"). Construye un FormData, añade los campos de texto y luego itera los archivos: 

this.filesToUpload.forEach(file => formData.append('files[]', file));
this.petitionService.create(formData).subscribe(...);

Laravel valida con 'files' => 'required|array|min:1' y 'files.*' => 'image|...', y guarda cada archivo en storage/app/public/petitions/ + registro en tabla files.

Edición

Truco clave: HTML+PHP no procesan bien PUT con multipart/form-data, así que el servicio Angular envía un POST añadiendo _method=PUT al FormData. Laravel lo interpreta como PUT automáticamente.

Borrado

DELETE /api/petitions/:id. El controlador llama a la policy delete y devuelve 403 si no es el autor. Borra también los archivos físicos del storage.

Manejo de errores en PetitionController

Todos los métodos están envueltos en try/catch con métodos auxiliares sendResponse / sendError que devuelven JSON uniforme:

{ "success": true,  "data": {...}, "message": "..." }
{ "success": false, "message": "...", "errors": {...} }

7. Firmar peticiones

PUT /api/petitions/sign/:id. El controlador comprueba con la policy sign que el usuario no es el creador (un autor no puede firmar su propia petición), revisa si ya firmó antes (belongsToMany petition_user), inserta el registro en la pivote y hace increment('signeds'). El show-component actualiza la signal localmente para mostrar el contador al instante.

Los errores 403 ("ya firmaste" / "no puedes firmar la tuya") se muestran al usuario con el mensaje exacto que devuelve Laravel.

9. Mis peticiones / Mis firmas

Mis peticiones

GET /api/mypetitions (auth obligatorio) devuelve solo las peticiones cuyo user_id coincide con el del usuario logueado. Ruta protegida con authGuard. El componente muestra una grid de cards con botones Editar y Eliminar.

Mis firmas

GET /api/mysigns usa la relación User::signatures() (tabla pivote petition_user) para paginar todas las peticiones que el usuario ha firmado. Solo aparece el botón Ver petición (no es el autor, no puede editar).

Ambos enlaces aparecen en la navbar y en el perfil cuando hay sesión y el usuario no es admin.

10. Buscador reactivo en la navbar

Implementado con un servicio compartido SearchService (app/services/search.service.ts) que expone una signal term.

  • La navbar contiene un <input type="search"> con [ngModel]/(ngModelChange) que escribe directamente en searchService.setTerm().
  • El ListComponent consume searchService.term y expone petitions como un computed() que filtra reactivamente por title.includes(term) sobre la lista cargada (no recarga del servidor).
  • El input solo se muestra cuando la ruta es exactamente /petitions: el componente escucha NavigationEnd y oculta el campo si estás en home, detalle, perfil, admin, etc. Además, al salir de /petitions el término se autolimpia.

public function handle(Request $request, Closure $next): Response
{
    if (!auth()->check() || auth()->user()->role !== 'admin') {
        return response()->json([
            'message' => 'Acceso denegado. Se requieren permisos de administrador.'
        ], 403);
    }
    return $next($request);
}

11.2 Pilar 2 – Rutas y controladores

Se crearon dos controladores separados para mantener la lógica limpia:

  • AdminController → peticiones
  • AdminUsersController → usuarios (Parte 2 del PDF)

AdminController

Devuelve las peticiones con los campos en español (titulo, descripcion, categoria, firmas_count...) mediante un mapPetition() auxiliar para que las vistas de los PDFs funcionen sin tener que cambiarlas.

  • indexPeticiones() – lista todas, paginado desc por fecha.
  • showPeticion($id) – detalle con relaciones.
  • updatePeticion() – acepta multipart con _method=PUT.
  • destroyPeticion() – borra petición + archivos físicos.

AdminUsersController

  • getUsers() – con withCount(['peticiones','firmas']) para mostrar los contadores en la tabla.
  • showUser($id) – ficha completa.
  • updateUser() – valida name/email/role, hashea password si viene escrita, no la toca si está vacía.
  • destroyUser() – regla de negocio: devuelve 403 con mensaje si el usuario tiene peticiones_count > 0 o firmas_count > 0. Es una protección de integridad referencial.

routes/api.php – grupo admin

Route::middleware(['auth:api', 'is_admin'])->prefix('admin')->group(function () {
    // Peticiones
    Route::get('/peticiones',         [AdminController::class, 'indexPeticiones']);
    Route::get('/peticiones/{id}',    [AdminController::class, 'showPeticion']);
    Route::post('/peticiones/{id}',   [AdminController::class, 'updatePeticion']); // _method=PUT
    Route::put('/peticiones/{id}',    [AdminController::class, 'updatePeticion']);
    Route::delete('/peticiones/{id}', [AdminController::class, 'destroyPeticion']);

    // Usuarios
    Route::get('/users',         [AdminUsersController::class, 'getUsers']);
    Route::get('/users/{id}',    [AdminUsersController::class, 'showUser']);
    Route::put('/users/{id}',    [AdminUsersController::class, 'updateUser']);
    Route::delete('/users/{id}', [AdminUsersController::class, 'destroyUser']);
});
Si un usuario sin rol admin (o anónimo) ataca cualquiera de estas rutas con Postman/curl, el middleware devuelve 401 (no autenticado) o 403 (no admin) antes de que el controlador llegue a ejecutarse.

export const adminGuard: CanActivateFn = () => {
    const authService = inject(AuthService);
    const router = inject(Router);

    if (authService.isAdmin()) return true;

    router.navigate(['/']);
    return false;
};

11.6 Store reactivo con caché + Pessimistic Update

El AdminService actúa como cerebro del panel. Mantiene dos signals peticiones y usuarios y dos banderas privadas peticionesCargadas / usuariosCargados. Cuando un componente entra en escena llama a cargar*Store(); si la bandera ya está a true el método retorna inmediatamente sin hacer HTTP → navegación instantánea entre Peticiones y Usuarios después de la primera carga. 

peticiones = signal<any[]>([]);
cargandoPeticiones = signal<boolean>(false);
private peticionesCargadas = false;

cargarPeticionesStore() {
    if (this.peticionesCargadas) return;          // ← caché

    this.cargandoPeticiones.set(true);
    this.http.get(`${API}/admin/peticiones`).subscribe({
        next: (res: any) => {
            this.peticiones.set(res.data ?? res);
            this.peticionesCargadas = true;
            this.cargandoPeticiones.set(false);
        }, ...
    });
}

Componente lista (sin ngOnInit)

export class AdminPeticionesListComponent {
    public adminService = inject(AdminService);
    peticiones = this.adminService.peticiones;       // ← espejo de la signal
    cargando   = this.adminService.cargandoPeticiones;

    constructor() {
        this.adminService.cargarPeticionesStore();   // ← le dice al servicio "carga si no tienes"
    }
}

Pessimistic Update

Cuando el admin edita una petición o un usuario y Laravel devuelve 200 OK, el componente le pide al servicio que actualice la signal localmente con los nuevos valores. Así al volver a la lista los cambios ya están reflejados sin hacer otra llamada al servidor. 

// admin-edit-user.component.ts
this.adminService.updateUserAdmin(this.id()!, payload).subscribe({
    next: () => {
        const usuarioEditado = { id: this.id()!, ...payload };
        this.adminService.actualizarUsuarioLocal(usuarioEditado); // ← refresca el store
        this.router.navigate(['/admin/users']);
    }, ...
});
// admin.service.ts
actualizarUsuarioLocal(u: any) {
    this.usuarios.update(users =>
        users.map(x => x.id === u.id ? { ...x, ...u } : x)
    );
}
Se llama pesimista porque desconfiamos de la red: la signal no se actualiza hasta que el servidor confirma con un OK. Lo contrario sería una optimistic update, que pintaría el cambio al instante asumiendo que el servidor no fallará.

11.7 CRUD de usuarios admin (Parte 2 PDF)

Es un _RUD, no un CRUD completo

El administrador no crea usuarios (los usuarios se registran solos). Solo:

  • Read: lista + detalle.
  • Update: name, email, role (user/admin), password opcional.
  • Delete: solo si el usuario no tiene peticiones ni firmas.

Regla de integridad referencial

Si intentas borrar un usuario con peticiones o firmas, el backend devuelve:

HTTP 403
{
    "success": false,
    "message": "No se puede eliminar: El usuario tiene peticiones creadas o firmas activas."
}

El componente captura ese mensaje y lo muestra en un alert.

Edición de password opcional

El campo password en AdminEditUser arranca vacío. Si el admin lo deja en blanco no se envía y la contraseña no se toca. Si escribe algo, Laravel la hashea con bcrypt y la guarda.

12. Estilos globales

El archivo src/styles.css importa Bootstrap 5.3 al principio (@import url(...)) y luego define la paleta corporativa. Importarlo desde el propio CSS — en vez de con un <link> en index.html — garantiza el orden de cascada: las reglas de Bootstrap se aplican primero y las nuestras debajo, así que ganan.

VariableValor
--bs-success (verde corporativo)#008001
--bs-primary (azul)Bootstrap por defecto #0d6efd

Los botones de acción de las tablas admin (Ver/Editar/Borrar) son sólidos (btn-primary, btn-warning, btn-danger) con texto blanco, separados con gap-2 y sin sombras complicadas.
